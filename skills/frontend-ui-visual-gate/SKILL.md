# Frontend UI Visual Gate

## Overview

在任何前端 UI 开发或调整进入架构、编码之前，先完成视觉方向对齐。这个 skill 用两个明确门禁把“要不要先看效果图”和“用户是否选定了方向”与后续开发隔开，避免 agent 因为改动很小、已有截图或时间紧就直接写代码。

## Trigger and state machine

把以下任务视为 UI 任务并触发本 skill：新页面、组件、布局、主题、颜色、字体、间距、响应式断点、交互状态、动效、可视化、表单、卡片、导航、按钮、UI 文案或“更现代/更高级/更舒服/更有信任感”等视觉与心理感受调整。

仅在以下状态转换后进入后续架构、开发和测试：

```text
UI 任务识别
  -> 视觉门禁 A：询问是否先生成效果图，并确认心理预期
      -> 用户拒绝：记录明确的跳过决定 -> 进入后续流程
      -> 用户同意：生成多种效果图 -> 展示并解释差异
          -> 视觉门禁 B：用户明确选择一个方向或组合方案
              -> 形成视觉决策简报 -> 架构设计 -> 开发 -> 回归验证
```

**硬性规则：**

- 未完成门禁 A 时，不开始架构、编码或测试实现。
- 用户同意生图后，未完成门禁 B 时，不开始架构、编码或测试实现。
- “小改动”“只有两处 CSS”“已有参考图”“时间紧”“先搭骨架再说”都不是跳过门禁的理由。
- 用户明确拒绝生图时可以继续，但要记录“已询问、用户拒绝、拒绝原因”；如果用户不愿说明，明确记录“用户拒绝提供原因”，不要把拒绝默认为同意。
- 用户没有明确选择方案时暂停并追问；“看起来都行”“你决定”“先做起来”不等同于选择，除非用户明确授权 agent 代选并接受该决定。

## 门禁 A：先询问视觉预期

在第一次确认任务包含 UI 工作后，立即发送简短问题，不要先输出架构或代码：

> 检测到这次任务包含前端界面/UI 开发或调整。开始架构与编码前，是否先生成 2–4 种效果图，用来确认视觉方向是否符合你的心理预期？你希望用户感受到什么（例如：专业、可信、轻松、高效、温暖、克制）？

按用户回答处理：

- **同意**：收集生成效果图所需的最少上下文：目标页面/区域、目标用户、核心动作、已有品牌或参考、必须保留与必须避免的元素。缺失信息使用明确标注的低风险假设，不要把多轮问答变成设计评审会。
- **拒绝**：确认“本次跳过生图，按文字需求/现有设计规范继续”，记录用户给出的原因；若用户不提供原因，记录“用户拒绝提供原因”，然后填写跳过版视觉决策简报，才能进入后续流程。
- **模糊或未回答**：只追问是否同意生图和心理预期；在得到明确回答前停留在门禁 A。
- **已有已批准 mockup**：询问用户是“直接以该 mockup 作为 source of truth”还是仍要生成变体；已批准 mockup 可以满足视觉对齐，但不能默默替用户选择。

## 门禁 B：生成、展示并让用户选择

用户同意后，使用 **REQUIRED SUB-SKILL: `$imagegen`** 生成视觉概念图。新图用于方向对比，不要把概念图冒充为可运行的代码截图或精确规格稿。

### 生成要求

1. 生成 2–4 个真正有差异的方向；默认生成 3 个，除非用户指定数量。
2. 保持可比性：相同页面目标、信息层级、主要 CTA 和关键内容，只改变视觉语言、构图、密度、色彩、字体气质或材质。
3. 方向应覆盖不同取舍，而不是同一张图换颜色。可按任务选择：
   - **Calm / Trustworthy**：留白、稳定层级、克制色彩，强调安心和可读性。
   - **Efficient / Productive**：信息密度、清晰分组、强操作反馈，强调效率和掌控感。
   - **Expressive / Editorial**：强标题、个性构图、明显视觉记忆点，强调品牌和探索感。
4. 使用现有品牌资产、产品截图或用户提供的参考图作为约束；没有参考时，说明关键假设。
5. 在展示结果时为每个方案附上：方案名、心理感受、视觉取舍、适合场景、主要风险。让用户看图时能比较，不要只说“这个更好看”。

展示格式应类似：

```text
方案 A — Calm / Trustworthy
心理感受：安心、专业、低压力
视觉取舍：高留白、柔和对比、弱装饰
风险：品牌记忆点和首屏冲击较弱

方案 B — Efficient / Productive
心理感受：清晰、快速、可控
视觉取舍：更紧凑的分组、强 CTA、明显状态
风险：信息密度过高时会显得工具化

方案 C — Expressive / Editorial
心理感受：有个性、值得探索
视觉取舍：强标题和大胆构图
风险：需要更严格的可读性和响应式约束
```

然后明确询问：

> 请选择 A、B、C，或告诉我“以 A 为主、采用 B 的 CTA / C 的配色”。在你明确选择前，我不会进入架构和编码。

### 选择处理

- 用户选择单一方向：记录该方向和不可丢失的关键特征。
- 用户选择组合：提炼成一份明确的组合决策；若组合存在冲突，先指出冲突并生成一次聚焦的修订图，不要自行裁决。
- 用户要求修改方向：只重生成相关变体，保留已认可部分，直到得到明确选择。
- 用户授权 agent 推荐：agent 可以提出推荐及理由，但仍必须让用户明确确认最终方向；“授权 agent 代选”本身不等于视觉门禁 B 通过。
- 用户反悔：回到门禁 B，更新视觉决策，不要让旧图继续作为 source of truth。

## 视觉决策简报与交接

进入架构设计前，先用短简报固定选择结果。即使用户跳过生图，也必须填写同一份简报，并把“视觉方向”写成“跳过生图，按 <source of truth> 实现”：

```text
视觉方向：<方案名或组合>
目标心理感受：<用户希望感受到什么>
必须保留：<层级、组件、品牌资产、CTA、内容>
视觉约束：<颜色、字体、密度、圆角、阴影、动效等>
响应式意图：<桌面、平板、移动端的布局变化>
无障碍底线：<对比度、键盘焦点、语义、缩放、动效降级>
明确避开：<用户不想要的风格或元素>
选择依据：<用户选择或授权代选的理由>
```

跳过生图时，至少补齐：跳过决定、必填的跳过原因、实现 source of truth（现有设计系统、已批准 mockup 或文字 brief）、不可变约束、响应式意图、无障碍底线和回归范围。将该简报作为后续架构、实现、评审和回归测试的 source of truth。概念图用于验证视觉层级和心理预期；代码实现可以因技术约束调整，但任何明显偏离都必须回到用户确认，不要静默改成另一个方向。

## 后续执行顺序

完成视觉门禁后，按项目实际情况继续：

1. 检查现有项目结构、设计 token、组件复用边界和测试工具。
2. 设计最小架构与组件契约，使其能表达已选的视觉方向，而不是反过来让架构决定视觉。
3. 按选定方向实现页面或组件，并优先复用现有设计系统。
4. 检查桌面、平板、移动端，以及 hover、focus、disabled、loading、error 等关键状态。
5. 做可访问性检查：语义结构、键盘操作、焦点可见性、对比度、文本缩放、替代文本和 `prefers-reduced-motion`。
6. 运行相关单元/组件测试、lint、构建和回归测试；对 UI 任务做浏览器或截图检查。
7. 将实现结果与选定概念图比较“层级、情绪、密度、CTA 优先级和响应式意图”，记录偏差及其技术原因。

本 skill 不替代项目已有的 brainstorming、TDD、系统调试或完成前验证流程；它是这些流程之前的视觉方向门禁。

## 常见失败与纠偏

| 常见说法 | 正确处理 |
| --- | --- |
| “只是两个 CSS 值” | 仍然是 UI 行为/视觉变化；先询问门禁 A。用户明确拒绝后才继续。 |
| “设计师已经给了截图” | 把截图作为 source of truth，询问是否还需要生成变体；不要擅自认为用户已批准当前实现。 |
| “时间不够了，先写再说” | 缩短为 3 张快速概念图和一次选择，不能把选择推迟到代码之后。 |
| “我先搭一个通用骨架，视觉之后再定” | 在门禁 B 前只允许收集上下文，不允许架构或实现；骨架应服务已选方向。 |
| “用户没明确说要效果图” | 本 skill 的触发条件是 UI 任务，不要求用户先说出“效果图”三个字。主动询问。 |
| “效果图已经生成了，用户没选就先做” | 生成不等于批准；没有明确选择就暂停。 |

## 红旗检查

出现以下任一想法就停止并回到对应门禁：

- “这个改动太小，不需要问。”
- “我可以先把代码写出来再让用户挑。”
- “已有截图，所以不用确认心理预期。”
- “用户说先开始，应该算选了方向。”
- “我知道用户会喜欢哪个，直接替他选。”
- “先做一个版本，反正之后可以改。”

如果已在门禁前写了实现代码，停止扩展改动，向用户说明已越过门禁，并重新完成视觉确认；不要用已写代码反向强迫用户接受视觉方向。
